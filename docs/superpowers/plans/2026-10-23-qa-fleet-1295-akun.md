# QA Fleet Testing 1.295 Akun ARIMA — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Menjalankan smoke, API, sanity, dan regression testing atas **1.295 akun** hasil `seed_akun_per_unit` (219 unit × 6 tingkatan role) secara bertahap, terdistribusi ke **minimal 10 subagent** dalam batch yang terkontrol, dan menghasilkan laporan temuan yang dapat direproduksi.

**Architecture:** Pengujian berjalan lewat Django test client terhadap **salinan DB per worker** (`sqlite3` backup API), bukan terhadap `db.sqlite3` bersama. Setiap worker memproses satu shard akun, menulis hasil JSON ke disk, dan agregasi dilakukan sekali di akhir oleh satu proses. Subagent tidak saling berbagi state: masing-masing menerima daftar username, daftar endpoint, dan direktori output sendiri, lalu mengembalikan ringkasan terstruktur. Ini menghindari dua masalah yang sudah diukur (lihat §Root Cause): rate-limit login 8/60s per IP, dan kontensi lock SQLite yang membuat 10 proses paralel **lebih lambat** daripada 1 proses bila DB dibagi.

**Tech Stack:** Django 6.1.1 (`.venv`, Python 3.12.10), `django.test.Client`, SQLite (`db.sqlite3`, 4,9 MB, `journal_mode=delete`, `busy_timeout=5000`), PowerShell/bash untuk orkestrasi proses, `delegate_task` untuk subagent, JSON sebagai format hasil antara.

**Spec sumber:** `docs/akun_per_unit_report.txt` (1.581 baris, 1.295 akun seed + 45 akun lama), `accounts/management/commands/seed_akun_per_unit.py`, `accounts/management/commands/report_akun_per_unit.py`.

## Root Cause Analysis — mengapa desain ini, bukan yang biasa

Plan QA naif ("login 1.300 akun lewat HTTP, GET semua halaman") **tidak bisa jalan** di repo ini. Tiga penghalang terukur:

**Penghalang 1 — login form dibatasi 8 request/60 detik per IP.** `accounts/views.py:17` memasang `@rate_limit(max_calls=8, window=60, scope='login')` pada `RateLimitedLoginView`. Key-nya per IP untuk user anonim (`akreditasi/security_utils.py:63`). Probe nyata:

```
POST /accounts/login/ x12 → [302,302,302,302,302,302,302,302,429,429,429,429]
Rate limit exceeded: rl:login:ip:127.0.0.1 (8/8 calls in 60s)
```

Artinya 1.295 login lewat form butuh **≥162 menit murni menunggu**, dan 10 worker paralel dari satu IP tetap kena limit yang sama. **Solusi:** pakai `Client.login()`, yang memanggil `authenticate()` langsung dan melewati view. Terverifikasi: 30/30 login sukses tanpa 429. Untuk tes yang tidak menguji password, pakai `force_login()` yang lebih murah lagi.

**Penghalang 2 — session DB membuat 1.295 login menulis 1.295 baris.** `SESSION_ENGINE = django.contrib.sessions.backends.db`. `force_login` membuat session row; dengan 10 proses paralel ini menjadi titik kontensi tulis. **Solusi:** `override_settings(SESSION_ENGINE='django.contrib.sessions.backends.signed_cookies')` selama pengujian, sehingga session tidak menyentuh DB sama sekali.

**Penghalang 3 — SQLite mengunci, dan paralelisme naif justru memperlambat.** `journal_mode=delete` (bukan WAL). Diukur pada beban 50 request/worker:

| Konfigurasi | Wall time | Throughput |
|---|---|---|
| 1 proses, 100 akun × 5 endpoint | 133 s | 3,8 req/s |
| 4 proses, 40 akun × 5 endpoint (DB bersama) | 19 s | 10,5 req/s |
| 10 proses, 100 akun × 5 endpoint (DB bersama) | 30 s | 16,7 req/s |
| 10 proses, 100 akun × 5 endpoint (DB **disalin** per worker) | 26 s | 19,2 req/s |

10 worker pada DB bersama hanya 1,6× lebih cepat dari 4 worker — sisanya hilang jadi lock contention. Dengan salinan DB per worker, throughput naik ke 19,2 req/s dan **tidak ada satu pun lock error** (`error/lock: 0` pada uji 40 akun × 5 endpoint). **Solusi:** setiap worker menyalin `db.sqlite3` lewat `sqlite3.Connection.backup()` (aman dibaca saat proses lain menulis), lalu mengarahkan `settings.DATABASES['default']['NAME']` ke salinan itu.

**Konsekuensi yang harus diterima:** tes hanya boleh **membaca**. Setiap POST yang mengubah data akan hilang setelah worker selesai (ditulis ke salinan). Karena itu API testing di plan ini dibatasi pada endpoint yang **idempoten/baca-saja** atau yang dampaknya memang tidak diharapkan (uji negatif: 403/400/405). Uji tulis yang sebenarnya dijalankan di **satu worker khusus** terhadap DB asli, dengan transaksi dibatalkan (`transaction.atomic` + `set_rollback`), dan hanya untuk endpoint yang sudah punya test sendiri di repo.

## Prinsip Plan

1. **Baca dulu, tulis belakangan.** Fase 1–3 hanya GET/POST negatif. Fase 4 (regression tulis) menyentuh DB asli dan wajib rollback.
2. **Setiap worker punya DB sendiri.** Tidak ada worker yang menulis ke `db.sqlite3`.
3. **Ekspektasi eksplisit per role.** Status yang diharapkan disimpan di `qa/expectations.py`, bukan disimpulkan saat runtime.
4. **Hasil selalu ke disk, bukan ke context.** Worker menulis JSON; agregator membaca JSON. Context subagent tidak dipakai sebagai tempat menyimpan 100.000 baris hasil.
5. **Satu shard = satu file = satu worker.** Tidak ada dua worker menulis file yang sama.
6. **Gate sebelum lanjut fase.** Fase N+1 tidak dimulai bila Fase N belum 100% akun terproses.

## Risiko & Mitigasi

| Risiko | Kemungkinan | Mitigasi |
|---|---|---|
| Subagent mengubah kode aplikasi | Sedang | Kontrak eksplisit "JANGAN mengubah kode"; verifikasi `git status` setelah tiap batch |
| 10 worker menghabiskan RAM | Rendah | 12 core, DB 4,9 MB; tiap worker ~150 MB → 1,5 GB |
| Shard yatim (file hilang) | Sedang | Gate menghitung 13 file; batch B-02/B-04/B-06/B-08 menutup sisa |
| Uji tulis bocor ke DB asli | Rendah | `rolled_back()` + verifikasi count sebelum/sesudah |
| Rate limit kena saat `Client.login()` | Rendah | `login()` melewati view; terverifikasi 30/30 |
| Temuan palsu dari F-2/F-3 | Tinggi | F-2/F-3 dicatat sebagai temuan yang sudah diketahui di `expectations.py`, bukan dilaporkan ulang 1.295 kali |

## Yang TIDAK dilakukan plan ini

- Tidak menguji alur tulis penuh (buat pasien, buat kunjungan, upload dokumen) — itu butuh data fixture per unit dan menjadi plan terpisah.
- Tidak menguji performa/load — beda alat (k6/Locust), beda tujuan.
- Tidak mengubah izin role atau `RolePermissionConfig` — F-3 dilaporkan, keputusan ada di operator.
- Tidak menjalankan migrasi ke Supabase produksi.
